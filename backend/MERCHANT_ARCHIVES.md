# Phase 24 商家导出与归档

本阶段仅开发源码。未运行测试、迁移、备份脚本、校验脚本、恢复操作或部署，也未连接生产数据库/R2。静态类型和语法检查不能证明微信或数据库运行成功。

## 数据与权限

复用现有微信会话、`permittedStore` 和店铺权限。新归档、历史、下载、预检查接口均仅允许 **owner**；原账单/经营分析继续保留 owner/manager 权限。每条归档及请求记录绑定 `store_id`，每次请求重新校验。不会导出 `auth_sessions`、令牌、服务端密钥、顾客身份、姓名、电话、详细地址、送达照片、订单备注或客服正文。经营配送配置是 owner 管理数据，可以包含配送中心坐标，不经过公开顾客接口。

历史与文件存入新增 `merchant_archives`，正文为私有 PostgreSQL bytea，没有公开对象路径、匿名下载链接或前端拼接的大归档。辅助表 `merchant_archive_actions` 用于数据库级频率控制。先应用既有 001—013，再由操作者应用 **014_merchant_archives.sql**；本阶段没有执行。原有账单/分析 CSV 导出不依赖新增表。

## API

基础路径 `/v1/merchant/stores/:slug/archives`，须 Bearer 认证：

- **POST 基础路径**：`{kind,clientKey,from?,to?}`。kind 为 catalog-json、catalog-csv、settings-json、orders-json、archive-json；后两项必须给出合法日期范围。返回历史记录与真实生成状态，不自动下载。
- **GET 基础路径**：`limit=20&before=游标`，最多50条，按服务端创建时间和UUID倒序游标分页，包含类型、时间、字节数、摘要、生成/就绪/失败状态、失败代码、到期时间及 downloadable。
- **GET `/:id/download`**：授权检查后返回 `{filename,content,sha256}`，供现有小程序私有目录保存及文件分享模式使用。不提供匿名 URL。仅 ready 且未过期的同店记录可下载，返回前重新核对正文摘要。
- **POST `/preflight`**：`{content:"归档JSON原文"}`，返回校验结果、记录数、图片引用、当前数据库仍引用的图片数量、历史关联警告及 `restoreAllowed:false`。不调用任何商品、库存、订单或支付写入接口；只写请求限流记录。

状态码：401 未登录；403 非owner/非授权店铺/归档店铺不符；404 无可下载文件；409 幂等编号冲突、正在生成、存储上限或不兼容版本；400 参数或归档校验错误；413 超限；429 频率超限；503 服务异常。不在响应或日志输出上传归档正文及认证数据。

## 文件格式

结构化归档是一个可下载的、有限大小 JSON 包，不依赖 ZIP 库：

```
{
  "manifest": {
    "format": "stall-merchant-archive", "version": 1, "schemaVersion": 14,
    "store": {"id": "UUID", "slug": "店铺slug"},
    "kind": "archive-json", "createdAt": "服务端UTC时间",
    "currency": "CNY", "displayTimeZone": "Asia/Shanghai",
    "range": {"from": "YYYY-MM-DD", "to": "YYYY-MM-DD"},
    "files": [{"name": "products.json", "bytes": 123, "sha256": "...", "records": 1}],
    "omissions": ["明确列出的未包含数据类别"]
  },
  "files": {"products.json": "精确JSON文本，而非重新序列化后的对象"}
}
```

文件内容使用原始文本字符串，摘要按其 UTF-8 字节计算，避免解析/重新排版造成摘要歧义。完整店铺归档包含以下逻辑文件：

- categories.json：稳定ID、名称、排序。
- products.json：稳定ID及分类ID、描述、整数分原价和折扣、UTC折扣窗口、原始上架开关、手动售罄、库存模式/数量/阈值/版本、图片对象键、UTC上架计划、版本和创建/修改时间。定时到达的有效上架状态仍按现有服务端发布规则计算，不把原始 active=false 误认为计划丢失。
- drafts.json：原始表单 payload、版本、draft/published/discarded状态、已发布商品ID、创建/修改时间。原始未完成价格、分类和日期输入不强行转换为正式商品值。
- settings.json：原有配置整行内容、配置 MD5 revision、更新时间，保留营业、公告、起送金额、配送区域稳定ID及坐标范围、时段/星期/区域关联、特殊日期及暂停状态。未配置时明确 configured=false，不生成设备默认值。
- orders.json：所选日期内订单ID、原始金额与支付标签/履约状态、创建及修改时间、库存占用状态；排除顾客身份和收货数据。
- order-items.json：原始明细ID、order_id、历史商品ID、历史名称、成交单价、数量、成交小计、已有分类历史快照。即使当前商品已删除或改价也不重新关联名称或当前价格。
- order-summary.json：包含取消的总订单金额、不含取消的订单金额、取消金额、非取消未支付金额、数量。使用整数分十进制字符串合计，已确认收款及确认支付数量固定为0：当前没有可信微信支付核验链路，不能依据 paid 标签、库存或送达状态宣称已收款。

商品 CSV 使用 UTF-8 BOM、中文表头、完整转义和公式注入防护。正式商品价格为分，草稿保留原始元输入，列名明确区分；日期保留UTC或注明草稿原始值/店铺时区。分类、商品、草稿用记录类型区分，不通过名称生成新ID。JSON 保留原值，不能将 CSV 当作直接恢复文件。

经营归档**不包含**图片实体、库存流水/预留明细、支付事件、客服会话和认证信息；它不是可直接恢复整个系统的数据库副本。客服消息目前没有单独导出功能，不会通过普通店铺归档扩散。

## 一致性、限额与历史

各个 JSON 数据文件在同一只读 REPEATABLE READ 事务内读取，参数化SQL、每条语句5秒限制；数据查询之间还有20秒预算检查（单条查询可能延伸至下一次检查，不能视为严格20秒任务取消器）。订单日期采用 Asia/Shanghai 边界，最多366天；数据库时间为UTC语义的 timestamptz，界面显示北京时间。

同步导出上限：4MiB正文、2000分类、5000商品、5000草稿、5000订单、20000订单明细。超过上限明确失败，不截断后冒充完整归档。完整归档的商品/分类/配置为当前全集，订单**仅所选日期范围**；更大店铺目前需管理员系统备份，未实现分片或后台大归档。

每店最多1个正在生成的任务、10个未过期文件、每小时5次新生成；预检查每小时10次，下载每分钟30次。限流用数据库事务锁，跨进程生效。生成请求使用店铺内唯一 clientKey，相同参数重试返回原记录，改变参数返回409。小程序发送锁及超时重试继续使用原编号；离开页面后可从历史核对。

先持久化 generating，再生成；成功写入 ready，异常写 failed。进程中断后，超过2分钟的 generating 在后续历史读取或生成请求时标为中断失败。文件7天后拒绝下载；过期正文在后续历史读取或生成时惰性清理，历史元数据保留。**没有后台清理计划或自动备份任务**，无人访问时不保证到点物理删除。失败记录、过期记录和请求成功均不等于灾难恢复备份成功。

## 复用账单与分析

备份页日期范围账单 CSV 直接调用已有 `/billing/export`，分析仍进入原页面使用 `/analytics/export`，未复制统计模块。账单 CSV 补充成交单价/小计快照及独立取消金额列，普通账单页面原显示结构保留，默认不含顾客隐私。账单/分析保留既有限额（5MiB、日期/记录上限、SQL超时），另共用**单Node进程每店每分钟5次**基本导出限流；此基础保护不会声称在多进程或重启后维持全局频率。新归档限流为数据库级实现，两者明确区分。

## 恢复安全基础与边界

预检查核对格式/版本、店铺归属、固定文件清单、每文件摘要/字节数/记录数、必需字段、稳定ID唯一性、商品分类引用、草稿发布商品引用、订单与明细引用和成交金额合计、配送配置原有规则、图片对象键的同店路径。历史商品删除不按当前名称重建，返回警告；草稿缺失分类保留原始内容并提示。

图片仅检查路径和当前数据库引用，不向R2发请求，**不证明对象仍存在或已经备份**。摘要只能证明内部一致性，不证明来源真实性；攻击者能重算摘要，故本阶段从不执行恢复、不承诺上传文件业务可用。未来还需独立隔离环境、可信来源/签名、完整业务校验、权限复核、冲突处理和经批准的恢复流程。

## 系统级脚本（只修改源码，未运行）

复用 backup-db、backup-r2、verify-db-backup、verify-r2-backup，增加共享 backup-metadata 帮助模块：

- metadataVersion=2、独立 backupId、backupSetId、开始/完成时间、ready/failed、文件清单、字节数、SHA-256和 manifestSha256。
- 操作者显式给两个备份运行设置同一个 UUID 格式 BACKUP_SET_ID，关联数据库与对象备份；未设置时各自随机ID且 pairedSetExplicit=false，不能假装已经配对。
- 实际数据库迁移版本不通过猜测填写：schemaVersion=null，记录当前应用预期版本14；数据库真实结构与迁移历史须在受控恢复时检查。
- 数据库仍为 pg_dump custom 格式与 pg_restore --list 静态结构校验；对象仍是受保护私有目录下的流式副本，包含键、ETag、可用VersionId/修改时间/MIME和内容摘要。
- 失败有受保护的失败元数据；未完成R2目录不标有效，数据库工具输出不打印连接信息。旧v1清单仍可校验但明确缺少新批次和清单摘要；新校验器核对清单摘要、文件列表及可选预期 BACKUP_SET_ID。
- 清单摘要不是签名；文件权限不能替代加密或异地存储。两次备份不构成事务一致快照，桶遍历本身也不是事务快照；需要后续校验数据库图片引用、源对象完整性及隔离恢复演练。recoveryVerified=false，不宣称恢复成功。

小程序没有系统备份执行/恢复入口，也没有定时备份。

## 手动体验与后续验证

由操作者先准备隔离环境和已按序应用至014的数据库，本阶段未代为执行。用有owner权限的现有商家会话打开工作台“数据备份与恢复”，生成不同类别并查看真实状态，下载JSON/CSV；设置日期范围检查订单快照、取消金额和确认收款0。选择已下载归档进行预检查，查看计数和图片提示；更改文件摘要、店铺、版本或关联，应拒绝校验且不改业务数据。用其他店铺/普通顾客账号检查访问拒绝。断网、重试、切换店铺及退出身份，不能看到本机替代导出或其他店铺历史。移除云端配置后，原本机导出/恢复只处理本机键值。

这些步骤尚未实际执行。下一阶段优先进行获授权的数据库与微信文件分享联调、并发/限流/超限验证，以及受控的系统备份与隔离恢复演练；不自动启动下一阶段。
