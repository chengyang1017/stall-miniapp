# Phase 21 配送管理云端整合

本阶段只完成源码开发和静态 TypeScript／Node 语法检查，没有运行测试、数据库迁移、部署或 Git 操作，没有连接生产数据库，也未生成备份。没有在数据库或微信环境验证功能。

## 商家页面

继续使用现有 `pages/delivery`，保留卡片、中文界面、配送中心选择和半径编辑。没有新增独立后台、地图系统、骑手定位或配送收费。

- 区域：新增、改名、启停、删除、上下移动调整顺序。数组顺序即顾客区域选择顺序，ID 在改名／重排时保持不变，支持小区、街道和任意商家自定义名称。
- 时段：新增、名称和起止时间编辑、适用星期、所有区域或指定区域、启停和删除。选择区域的集合明确保存在时段中。
- 特殊日期：新增／更新日期、暂停、恢复按正常周计划配送、删除规则。恢复不强制突破营业时间、星期或区域规则。
- 临时整体配送暂停：独立 deliveryPaused 开关，不修改店铺 accepting，也不修改单个区域、时段或日期的开关。
- 概览显示当前配置的启用区域／时段数量，未读取时不显示虚假正常状态。所有修改先进入草稿，点击“保存全部配送修改”才保存；有未保存提示、保存中、成功、失败、无权限和冲突提示。重读草稿前确认丢弃，失败保留输入。
- 删除区域会清除时段对该区域的引用；若某个限定区域时段因此没有区域，自动将该时段置为暂停，不会悄悄扩展为所有区域。

云端配置未建立时显示空区域／空时段，由商家自行新增；绝不取本地演示默认区域和时段上传。新增区或时段的输入需先点击新增进入草稿，再保存，不会只显示成功却丢掉尚未加入的输入。

## API 与权限

复用原接口，没有新增配送 URL：

### GET /v1/merchant/stores/:slug/delivery-rules

验证既有商家会话、店铺和 owner／manager 角色。返回 configured、rules、updatedAt、revision；revision 与 Phase 20 营业设置使用同一份完整 JSONB 内容摘要。

### PUT 同一路径

请求仅允许以下字段：

```json
{
  "expectedRevision": "上一次读取的摘要，首次配置为 null",
  "areas": [],
  "slots": [],
  "specialDates": [],
  "deliveryPaused": false
}
```

支持局部配送字段更新，必须包含 expectedRevision。拒绝 accepting、days、notice、minimumOrderCents 等营业字段，避免页面互相覆盖。**旧版不带版本的完整 PUT 请求会被拒绝，需要升级请求格式**，不保留绕过版本保护的旧写法。

事务先取得 stores 的 NO KEY UPDATE 锁串行化首次配置，再锁配置行核对 revision；冲突409，不静默覆盖。仅将允许的配送字段合并到数据库当前配置，保留营业时间、公告、起送金额及未知扩展字段。Phase 20 营业 PATCH 仍仅允许自己的字段，同样检测完整配置的版本变化。

首次建立配置继续使用 Phase 20 服务端基础值：接单关闭、空公告、0分门槛、默认营业周计划及空配送区域／时段；不是从手机复制营业配置。商家需到营业管理确认接单和营业设置。

### GET /v1/stores/:slug/delivery-rules

只读公开投影，仅对活动店铺提供必要选择信息：区域 ID／名称／启停／是否需要地图位置、启用时段及星期／区域关联、日期暂停、整体暂停、营业状态及服务器时间。停用区域保留名称和状态，用于明确提示旧地址不可配送。不会公开配送中心坐标、半径、商家版本摘要或管理接口权限。

已有公开 business-settings 继续读取同一份 JSONB，并反映整体暂停及今天的日期暂停。读失败不会切换本机数据。

## 数据结构

继续使用 `store_delivery_rules.configuration`，不建第二套表，不新增 SQL migration。迁移004是已有表依赖，下单仍依赖现有订单和库存结构；本阶段没有运行任何已有迁移。

- `areas[]`：保留 id、name、enabled、latitude、longitude、radiusMeters；顺序由数组表示。
- `slots[]`：保留 id、label、start、end、enabled，新增可选 `weekdays:number[]`（周日0至周六6）、`areaIds:string[]`。
- `deliveryPaused:boolean`：缺失表示 false。
- `specialDates:{date:string,paused:boolean}[]`：缺失为空。日期为北京时间 YYYY-MM-DD，唯一；paused=false 表示按正常周计划，不代表强制营业。
- 旧时段缺少 weekdays 时按每天处理，缺少 areaIds 时按所有区域处理。明确的空 areaIds 表示无区域，仅允许暂停状态，不会被当作“所有区域”。

商家表单及后端验证：最多30区域、30时段、366日期；名称、时间、星期、区域引用、唯一 ID、真实日历日期及地图数据均检查。区域名称不允许重复；写入时启用时段在相同区域、相同星期不能重叠。旧配置读取不因为历史重叠被自动改写；商家再次保存配送配置时需消除冲突。

API 请求上限128KiB。时段不支持跨日。保留已有地图半径100–100000米和配送日期今天至未来7天的规则。

## 顾客端与地址

首页、购物车、结算和地址页统一采用有效 MerchantContext；无有效配置才进入演示模式，网络失败不会自动切换模式。

- 首页显示真实启用区域摘要和暂停说明；配送读取失败仍可浏览商品，但明确说明配送暂不可核对。
- 购物车显示所选区域及今日可用时段，允许进入地址选择；特殊日期今天暂停时可在结算选择符合规则的其他日期，不把日期暂停当作整体配送暂停。
- 地址仍在个人设备存储，区域选择来自云端。增加可选 deliveryAreaId、deliveryStoreKey，绑定稳定区域 ID 和 API／店铺上下文，不按名字重新绑定删除后重建的区域。
- 老地址没有绑定信息时，仅在当前云端区域名称唯一匹配时作为候选；用户选择使用或设为默认后在本地建立明确绑定。不同店铺的已有绑定不能直接用于当前店铺，需编辑重选。停用、删除或歧义区域明确显示不可配送。
- 有地图范围的区域要求地址有坐标；精确半径由服务器最终校验，不公开商家中心位置。没有新增地址地理编码服务。
- 结算重新进入时重读规则，按区域、配送日期、星期、启停和特殊日期重新计算时段，保留仍有效的选择、清除失效选择。时段列表显示名称与起止时间。切换日期、地址或时段后重新核对。
- 日期和当日时段过滤使用接口服务器时间及经过时间，按北京时间展示；前端不是最终裁决。

## 服务端下单与历史订单

verifyDelivery 在原下单事务中读取并共享锁定当前规则，依次校验店铺接单、整体配送暂停、当前营业时间、区域启用及地图范围、未来7天日期、特殊日期、目标星期营业、时段启用／适用星期／区域／营业区间和当日结束时间。等待商品锁后仍复核时间边界。客户端篡改 areaId、slotId、日期或暂停状态不能绕过这些检查。

保持 Phase 20 起送金额检查及原有库存、幂等、支付边界。不会模拟收款、自动付款、自动撤销既有订单或增加运费。

新订单额外把服务端区域名称保存在 contact_snapshot 和 delivery_slot_snapshot，时段仍保存名称、时间、日期及区域 ID。商家订单页和订单详情优先展示这些快照；配置删除、改名、暂停不更新已下单订单。旧订单没有名称快照时保留原 ID，不用现配置猜测旧名称。既有订单的幂等重试仍返回原订单，不重新套用新规则重建订单。

## 本机演示
