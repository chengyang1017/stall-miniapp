# 微信商城交付计划 B｜朋友 / 微信小程序前端与平台验收（直接交给 Codex）

> 项目：`chengyang1017/stall-miniapp`
> 执行人：协作开发者（朋友）及其 Codex
> 目标：将顾客与商家小程序从源码/演示推进到可在微信开发者工具、真机和客户环境中稳定使用的交付版本。
> 目前使用微信测试号：**可先做本地页面开发、构建和演示；正式 AppID、登录、支付、提审及部分受限能力必须等客户提供权限后验证。**

## 0. 给 Codex 的执行规则

1. 先检查 GitHub 最新 `main`、本地工作区和当前分支，优先阅读 `apps/BUILDING.md`、`backend/APP_SEPARATION_READINESS.md`、`docs/testing/RELEASE_CHECKLIST.md` 及实际前端源码。历史的页面数、命令与路径必须以当前仓库为准。
2. **无需借用项目负责人微信号或任何 AppSecret。** 可使用自己的微信号登录微信开发者工具；基础页面开发可尝试游客模式/个人测试号，能否使用真实 `wx.login` 等能力必须以实际测试为准。
3. VS Code/Codex 用于源码、npm 构建、静态检查与可运行的离线测试；**要看原生微信小程序界面请使用微信开发者工具**（或已配置的合法自动化工具）。若未安装微信开发者工具，先做不依赖它的任务并标记平台验证 `BLOCKED`，不能把 TypeScript 编译当作微信平台运行成功。
4. 朋友默认负责 `miniprogram/**`、`apps/**`、相关前端构建/界面测试、`docs/delivery/frontend/**`。**不要修改 `backend/**`、数据库 SQL、Phase8 Docker/镜像/凭据、生产配置或项目负责人的测试档案**；后端有错误时用 Issue/契约清单沟通，未经协调不要改服务端逻辑。
5. 所有功能区分 `DEMO`、`CLOUD-STAGING`、`WECHAT-DEVTOOLS`、`REAL-DEVICE` 和 `PRODUCTION`；不可从本地演示成功推断跨设备云端同步、正式微信支付或真机验收成功。
6. 使用短生命周期分支 `frontend/<feature>`，经过 PR 审核才合并到 `main`，不 force push、不覆盖别人的未提交工作。不在仓库或日志中加入登录令牌、顾客地址、手机号、支付或生产敏感信息。
7. 在仅涉及前端源码、离线构建与文档范围内主动执行任务；云端配置、正式小程序账号操作、支付交易、对外发布或需有费用的行为，必须单独获得授权。

## 1. 你的工作阶段

### 阶段 A：在自己的电脑启动开发环境（P0）

- [ ] 安装 Git、VS Code、Node.js（按仓库要求版本）以及微信开发者工具（平台预览需要）。安装本身不要求正式小程序商户账号。
- [ ] Clone 仓库，在 VS Code 中打开，执行项目当前规定的 npm 依赖安装、静态检查及构建命令；优先 `npm ci`（存在 lockfile 时）。
- [ ] 根据当前 `apps/BUILDING.md` 核验 `npm run build:combined`、`npm run build:customer`、`npm run build:merchant` 的实际行为与产物目录；不要仅凭过去记录假设能全部成功。
- [ ] 从 `dist/combined` 开始在微信开发者工具中导入/预览；记录实际使用游客模式/测试号/AppID 及遇到的权限限制。
- [ ] 建立自己的演示账号/安全假资料。不得连接旧 B0、未经授权的共享数据库或生产 API。
- **验收条件**：至少报告三目标的实测构建结果，以及能否在微信模拟器看到页面；没权限时提供原始报错并继续完成可离线任务。

### 阶段 B：完成首版顾客端（P0）

- [ ] 对首页、商品详情、分类/搜索、购物车、结算、地址、订单历史/详情、客服等页面做逐项检查。
- [ ] 分清本地演示与云端 API 路径；正式联调必须使用负责人提供的明确 staging API，不得默默回退演示数据并声称下单成功。
- [ ] 完善空数据、加载、超时、网络断开、请求重试、旧缓存和重复点击提示；订单价格、可售性必须以服务端验证为准。
- [ ] 测试未登录、用户切换、权限过期、跳转与小程序分享；尤其扫码进入正确店铺、新设备首次进入的流程。
- [ ] 记录每个页面状态与截图/测试证据；如尚未完成云端配置，标记 `CLOUD-STAGING NOT RUN`。
- **验收条件**：演示模式可用 + 真实 staging 在获授权后完成跨设备业务校验，不能混淆二者。

### 阶段 C：完成首版商家端（P0）

- [ ] 核验商品新增/编辑/上下架、分类、批量操作、库存、营业/起送金额/配送时段、订单列表与履约流程。
- [ ] 检查客服、送达凭证、账单分析和权限失败提示；后台数据必须与真实后端结果一致。
- [ ] 独立 Customer/Merchant 构建必须保持角色隔离；商家端不得把管理员功能暴露到顾客端产物。
- [ ] 检查不同商家权限、切店铺、重复提交、并发更新、网络断开、上传错误和图片授权读取行为。
- [ ] 前端发现服务端不满足需求时，提交可复现问题和接口差异，不在前端伪造可信支付或修改服务器状态。
- **验收条件**：客户可以按操作清单独立完成商家基本经营流程，在 staging + 真机完成实际验收前仅标记已实现/待验。

### 阶段 D：微信登录、支付交互与平台兼容（P0，权限依赖）

- [ ] 与负责人确定**首版 Combined 还是双 AppID**，默认不自行改成双 AppID。正式双 AppID 需要后端身份与扫码路由改造，不能只换项目配置。
- [ ] 核对微信开发者工具平台编译、包体积、基础库版本、隐私和权限声明、request/upload/download 合法域名以及 iOS/Android 行为。
- [ ] 根据负责人提供的可信后端支付协议接入 `wx.requestPayment` 与取消/失败/未知结果 UI；不能在客户端把支付回调直接当作数据库 `paid`。
- [ ] 准备微信小程序客户资料需求表：正式 AppID、开发者授权、支付商户绑定、备案、所需类目、域名和隐私政策；**由账号主体/负责人实际办理并批准，朋友不虚构已完成手续**。
- [ ] 不因目前使用测试号而停工。正式微信登录或支付受限时先提供占位接口、模拟 UI、真实错误记录，等待正式授权后再做真机/真支付测试。
- **验收条件**：能说明哪些已在开发者工具/真机实测，哪些因微信权限阻塞；真实支付最终结果由可信后端确认。

### 阶段 E：真机验收、客户培训与上线辅助（P0）

- [ ] Android + iPhone 测试：扫码进店、商品浏览、购物车、登录、下单、订单更新、客服、图片、网络切换与前后台切换。
- [ ] 商家端真机测试：商品管理、接单、配送、定位（若首版启用）、售后状态、权限边界与异常提示。
- [ ] 如果评价/GPS 仍未通过所需的微信权限、内容审核及后端可信支付检验，首版与负责人商定关闭或延期，不自行绕过。
- [ ] 编写客户使用手册、已知限制、常见问题、测试证据清单；辅助正式提审/发布，但**不得自行使用客户账号发布**。
- **验收条件**：针对首版发布范围，客户实际操作流程有逐项测试证据且无未处理 P0/P1 问题。

## 2. 强制留档：每完成任务必须更新 Markdown 并提交 GitHub

在自己的前端分支创建/维护以下文件，**追加记录、不删除失败历史**：

- `docs/delivery/frontend/PROGRESS.md`：任务 ID、负责人、状态、日期、分支、PR、代码修改与下一步。
- `docs/delivery/frontend/TEST_LOG.md`：实际运行的构建/测试命令、结果、微信开发者工具版本、使用的模式、截图/日志路径、失败详情。没运行写 `NOT RUN`。
- `docs/delivery/frontend/UI_CHECKLIST.md`：按页面记录 `DEMO` / `CLOUD-STAGING` / `WECHAT-DEVTOOLS` / `REAL-DEVICE` 验收情况，注明机型及账号权限条件。
- `docs/delivery/frontend/PLATFORM_BLOCKERS.md`：微信登录、AppID、域名、支付、备案等缺失权限、账号需求和客户协作事项。
- `docs/delivery/frontend/HANDOFF.md`：写给后端负责人的接口差异、错误码、所需测试数据、待确认协议与复现步骤。

不直接覆盖项目负责人维护的 `docs/testing/TEST_STATUS.md`、`TEST_HISTORY.md`、`KNOWN_ISSUES.md`、`docs/delivery/RELEASE_GATE.md`；在自己的档案中引用原文件，并在 PR 描述中请求负责人整合。

**每个 PR 必须包含**：任务 ID、截图或可复现页面路径、实际测试命令/设备结果、未验证项、已知风险、文档链接、后端 API 依赖、回退办法、Commit。缺少文档和测试证据的任务不能标记完成。

## 3. 两个人并行开发和沟通协议

- 前端任务用 ID 如 `FE-01`；后端任务用 `BE-01`。工作分支建议 `frontend/fe-01-devtools-baseline`。
- 需要服务端接口更改时，先填 `docs/delivery/frontend/HANDOFF.md`，给出路径、请求响应样例、当前错误及期望行为；负责人确认后再联调。
- 朋友无需拿到项目负责人的 Windows Docker 或数据库密码。优先使用隔离的 staging API 或 mock/演示模式，但必须如实标记测试层级。
- 微信测试号、游客模式与正式 AppID 权限互不等价；不要借用他人的微信账号，也不能直接用测试号当客户正式发布身份。
- 不在正式微信后台、生产服务、真实支付商户号上进行未经允许的变更。

## 4. 交给 Codex 的第一轮实际行动

**立即执行**（不涉及客户微信账号授权、真实支付或生产部署）：

1. Clone 最新仓库，确认 `main` 最新 HEAD、依赖、构建命令、工作区状态。
2. 创建自己的 `frontend/fe-01-devtools-baseline` 分支和 `docs/delivery/frontend/` 五份档案。
3. 按当前项目构建说明，分别执行 Combined、Customer、Merchant 的构建与边界检查，记录成功、失败、跳过；不假设历史结果仍有效。
4. 静态巡检顾客/商家首版页面、演示与云端数据入口，整理缺陷及优先级；可以修复**明确证据支持的纯前端 P0/P1 Bug**，不改后端协议。
5. 如果本机已安装微信开发者工具且可登录/游客预览，实际导入 Combined 并记录画面与权限；否则将其列为 `BLOCKED / NOT RUN`，继续做静态任务。
6. 提交并推送自己的分支，提交 PR 供项目负责人审核；不得直接覆盖 `main`。
7. 输出 FE-02 的下一步建议，以及需要后端负责人和客户提供的依赖。
